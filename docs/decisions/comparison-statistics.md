# Local-calendar comparison statistics

September 13, 2026. Proposed implementation policy, not delivered functionality. Owned change: this document only. Reviewed the implementation plan, foundation, heat-science research, `packages/comparison/src/index.ts` and tests, comparison contracts, and the separate [long-baseline design](climate-jobs.md). Documentation browsing only; no live weather requests.

## Version and scope

Introduce `era5-local-comparison-v2` for 2–5 distinct cities and 1–366 inclusive local calendar dates. Preserve `era5-comparison-v1` exactly: it currently has five fields, UTC windows, equal-hour available-value means, no daily/monthly grouping, and common-valid counts that do not change individual means. Its strict source URL requires the exact five-field list; adding fields or changing calendars in that path would break provenance validation. Existing location contracts have no timezone. New schemas, provider requests, cache identities, job kind and exports must be coordinated by the lead.

Proposed query adds a literal version and an IANA `timezone` to each location. Result includes `calendarPolicy:'location-local-v1'`, `coveragePolicy:'complete-days-v1'`, `distributionPolicy:'nearest-rank-v1'`, selected local dates and actual UTC bounds per city, dataset requested versus known constituent, fixed source grid/elevation, retrieval times, source request identity and calculation method per derived field. Persist timezone resolver/runtime tzdata version when available and resolved day boundaries so a later timezone database update cannot reinterpret an old result. Reject unsupported timezone/calendar boundaries explicitly.

Keep multiyear baseline/recent jobs separate. The UTC long-baseline proposal is not silently changed by this document; local-calendar multiyear results require their own version, bounds and resource review. A completed one-year comparison does not establish climatological normals, trends, homogeneity or complete multiyear support.

## Calendar and coverage rules

For each city construct midnight at the first selected date and midnight after the last selected date in its own timezone. Instant samples belong to `[start,end)`. Enumerate expected UTC hourly instants, then group by local date. Normal US modern civil days contain 24 samples, spring transition 23, autumn transition 25. Repeated wall-clock hours remain distinct by UTC instant and offset; nonexistent hours are not missing. Retain February 29. Never use one frozen UTC offset, slice an ISO UTC date to get local date, or divide elapsed time by 24 to count civil days.

Precipitation and sunshine use preceding-hour amounts: the row at time `t` represents `[t−1h,t)`. Include the closing row at local midnight after the last date, assigning it to the preceding date. Fetch UTC date padding sufficient for every city's bounds and closing interval; exclude padding from denominators. Chunk overlap/carry must count each instant/interval exactly once. Reject duplicate/conflicting rows, changed grid/method, query mismatch, malformed units or incomplete chunk delivery; distinguish these job errors from valid source missing values.

For historical zones with non-hour-aligned midnight or offset transitions, hourly totals cannot be split exactly into civil days. Initial implementation should reject those selections with `unsupported_calendar_alignment`, not prorate precipitation/sunshine or invent subhourly temperatures. This matters for old dates even within today's US geography. The plan must examine all requested day boundaries, not only the first date.

Coverage is independent per variable and bucket. Keep `expectedSlots`, `validSlots`, `absentSourceSlots`, `nullSlots`, and `methodExcludedSlots`, partitioning expected slots exactly. Exclusions are applied after source presence/null checks. Missing never equals zero and is never interpolated. Expose expected/complete/incomplete local day counts and first/last valid times. A complete day requires every expected slot for that variable to be valid; this 100% rule is an application reproducibility policy, not a WMO completeness standard or scientific representativeness threshold.

Each headline period statistic is populated only if every selected day is complete for its inputs; otherwise `value:null` with `partial` or `no_data`. Also return an explicitly named `availableCompleteDays` summary when at least one complete day exists, with its exact date support and denominator. Available-hour distributions/extremes may include incomplete days, but must be labeled accordingly. Do not silently promote those into period headlines. Full coverage remains descriptive modeled data, not accuracy validation.

For city comparisons provide a second support family: intersection of complete **local date labels** across every city, separately per metric. Calculate each city's daily statistics on those dates, then aggregate equally by day. This compares the same local dates, not simultaneous UTC instants. Retain individual coverage too. Disable automatic best/worst ranking on unequal support; common dates still do not eliminate model bias. A UTC-slot intersection, if retained, must be separately labeled and must not masquerade as common local days.

## Exact statistics

Use canonical Celsius/mm/seconds for calculations, fixed chronological compensated sums, no intermediate display rounding. Convert units only for presentation/export. All averages below are arithmetic descriptive means, not personal heat guidance.

| Output | Definition |
|---|---|
| Daily mean temperature or ordinary wet bulb | Sum of all valid hourly instant samples / expected samples, only on a complete day. This is the mean of hourly samples, not `(daily high + daily low)/2`. |
| Daily high / low | Maximum / minimum of complete day's hourly samples. Label as hourly-sample high/low; unobserved between-hour extremes cannot be recovered. |
| Month/selected-period mean | Equal-weight mean of its complete daily means. Headline requires all dates; separately named available summary uses complete dates only. |
| Average daily high / low | Equal-weight mean of complete daily maxima / minima. Ordinary wet-bulb average daily maximum follows the identical rule. |
| Full calendar-year mean | Sum of the daily means / 365 or 366. Equivalently weight each complete monthly mean by its number of days; never average 12 monthly means equally. An arbitrary selected range is labeled selected period, not annual. |
| Peak / minimum with dates | Extremum of all selected valid hourly samples; period headline only when complete. Otherwise expose `availableSamplePeak/Minimum`. Return UTC time, local date/time and offset; earliest UTC occurrence plus exact tie count. Compare unrounded canonical values for ties. Never call these all-time records. |
| Hourly distribution | All valid hourly samples in the bucket, including partial days; missing/excluded counts separate. Every sample has equal weight, including both autumn repeated hours. Clearly distinct from equal-day means. |

For at most one year use exact sorted valid samples for percentiles p=0.05, 0.25, 0.5, 0.75, 0.95: rank `ceil(p*n)`, one-based; n=0 gives null. Name the method; p50 need not equal the conventional average of two middle values. Do not average monthly percentiles. For an optional histogram use fixed ordinary-wet-bulb Celsius edges `−20,−19,…,50`, with underflow `<−20` and overflow `>=50`; each finite interior bin is `[lower,upper)`. No clipping: counts sum to valid samples. These are display bins, never heat categories. Fahrenheit selection converts those same edges rather than rebucketing the data. If a larger multiyear implementation uses approximate quantiles/histograms, return its distinct method and precision; never call approximate values exact.

When later computing multiyear monthly averages, expose two distinct statistics if needed: pooled complete-day mean (days are weights, leap days retained), and equal-year mean of complete year-month means. They differ; this policy's default is pooled days. Annual totals and annual event counts may be averaged across fully complete years, with years as explicit denominator. Missing years are not zero and no annualization is permitted.

## Ordinary wet bulb, not WBGT

Prefer the provider field only after the provider owner verifies historical availability, units, temporal semantics and method. Existing research identifies Open-Meteo's pinned helper as a pressure-independent Stull approximation; that is not proof of the currently deployed historical route. A repository search found no existing local TypeScript Stull implementation to reuse. Existing WBGT solver inputs must not be fabricated to supply this metric.

[Stull's original paper](https://doi.org/10.1175/JAMC-D-11-0143.1) describes an empirical sea-level fit for air temperature −20 to 50°C and RH 5–99%, with a cold/dry exception. It does not justify pressure correction, universal altitude validity, or personal hazard thresholds. Reference-domain error figures are not uncertainty bounds for reanalysis city comparisons.

If the field is unavailable, a separately tested `stull-2011-local-v1` fallback can derive **each hour** from co-timed Celsius air temperature and percent RH; never apply a nonlinear wet-bulb formula to monthly mean inputs. Freeze one method for all cities and chunks of a comparison; do not fill sporadic provider gaps with a second method. Preserve input availability and calculation failure reasons separately.

Concrete conservative fallback admission proposal: finite T in `[0,50]`°C and RH in `[5,99]`%, with both inputs present; otherwise derived value null. Excluding all negative air temperatures is an explicitly narrower application domain to avoid inventing a numeric cold/dry exception contour; it is not Stull's published lower bound. Record `pressureTreatment:'standard-sea-level-approximation'` and `pressureApplicability:'not_assessed'` for every value. No invented elevation/pressure cutoff or adjustment. This produces descriptive sea-level-approximation estimates at the input T/RH, not validated actual wet bulb at mountain locations. UI must expose this method limitation; a pressure-aware implementation would need independent reference validation and a new method version. Do not claim a complete winter wet-bulb mean when excluded hours are missing.

Retain raw provider values and any provider domain warnings in provenance; do not silently apply the proposed local fallback domain to the raw field or call every non-null provider value scientifically in-domain. Lead/provider owner must freeze that product's admission policy before comparing it with locally derived data.

## Precipitation, sunshine and cloudiness

[Bureau of Meteorology ETCCDI definitions](https://www.bom.gov.au/climate/pccsp/about-pi-extreme-indices.shtml) use daily precipitation of at least 1 mm for a wet day. Adopt `precipitationDayThresholdMm:1` with inclusive `>=`, on a complete local day's precipitation total. Include rain plus frozen-precipitation water equivalent as supplied; label “Precipitation days (≥1 mm)”, not rain-only days. Compare in canonical units; 1 mm is approximately 0.03937 inches and must not become a 0.04-inch calculation cutoff. Values below threshold are “<1 mm days”, not necessarily rain-free.

Return `knownWetDays`, `knownBelowThresholdDays`, `unknownDays`; these sum to selected dates. An incomplete day remains unknown even if its available sum already exceeds 1 mm, for a consistent complete-day policy. A headline period count requires zero unknown days; otherwise display e.g. “7 qualifying days among 28 complete days; 3 unknown.” Precipitation `totalMm` requires all intervals; `sumAvailableMm` is explicitly partial and never scaled. Do not infer days from precipitation probability, severe weather code, or the number of precipitating hours.

[Open-Meteo historical documentation](https://open-meteo.com/en/docs/historical-weather-api) defines sunshine duration in seconds for the preceding hour using a 120 W/m² direct-normal-irradiance criterion. Use validated supplied sunshine duration, sum seconds and divide by 3600 for hours; no DIY threshold on global shortwave or hourly-mean DNI to infer within-hour duration. Each hourly duration must be finite in `[0,3600]`. Complete daily/period totals and average daily hours follow the same missingness rules; retain partial available totals separately. Zero is legitimate, including polar night. Sunshine is not daylight, cloud-free time or a guarantee of a pleasant day. Numeric sunshine hours are the primary output; no unsupported “sunny day” threshold.

Cloud cover is independently useful. [NWS Honolulu's complete marine sky-cover table](https://www.weather.gov/hfo/New_Product_Help) supplies percentage boundaries 5,25,50,69,87. Apply the following bins to each **complete local day's mean total modeled cloud cover**, with equal hourly sample weights within the day:

| Daily mean total cloud fraction (%) | Neutral application label |
|---|---|
| 0–5 inclusive | 0–5% cloud |
| >5–25 | >5–25% cloud |
| >25–50 | >25–50% cloud |
| >50–69 | >50–69% cloud |
| >69–87 | >69–87% cloud |
| >87–100 | >87–100% cloud |

The boundaries are sourced meteorological descriptors; applying them to a whole-day modeled total-cloud mean is our descriptive aggregation, not an official NWS forecast classification. NWS sky wording can concern opaque cover and day/night periods; do not relabel total modeled cloud as opaque observed sky or call a full-day mean “sunny.” Return six disjoint day counts plus unknown days, and a daily mean cloud-cover percentage. No rounding before classification. All-day means include nighttime; a daylight-only product needs verified solar-time inputs and a separate policy. Cloud bins partition complete cloud days only; precipitation and sunshine may overlap any cloud bin. Do not use a single exclusive sunny/rainy/cloudy pie chart.

## Implementation acceptance cases

1. New York 2024-03-10 yields 23 expected samples; 2024-11-03 yields 25 and two distinct 01:00 instants. Honolulu and Phoenix ordinary dates stay 24. February 2024 has 29 dates. Check older non-hour-aligned boundaries fail explicitly.
2. Rain/sunshine at closing midnight belongs to the previous local date exactly once, including chunk/month/year boundaries. A missing closing amount affects that day's amount only, not midnight-start temperature.
3. A 24-slot day missing one temperature gives null daily headline high/low/mean, but 23 available hourly distribution samples. Missing humidity excludes derived wet bulb without suppressing valid temperature. All-null, absent, and excluded counts partition correctly; zero precipitation/sunshine is valid.
4. Two complete days with daily means 10 and 20 produce 15, even if one has 23 samples. January mean 10 and February 2024 mean 20 give `(31*10+29*20)/60=14.833333…` for those two months. Equal-hour output is separately identified.
5. Samples `[1,2,3,4]` yield nearest-rank p50=2, p95=4; changing units preserves ranks, histogram membership and ties. A hotter value on a partial day appears in available-sample peak, never an invented complete-period record.
6. Complete day totals 0, 0.9, 1.0 mm give two below-threshold days and one precipitation day. Missing amounts produce unknown, never dry. Wet days plus below-threshold plus unknown equals expected dates.
7. Cloud means exactly 5/25/50/69/87 fall in their lower bins; 100 in final bin; negative/>100 reject; null day goes unknown. Six counts plus unknown equals dates. A wet day with sunshine increments independent summaries without contradiction.
8. Local fallback T/RH boundaries 0/50 and 5/99 accepted; outside, null, nonfinite and negative T excluded explicitly. Wet-bulb of monthly means is never used. Unsupported provider field does not silently change source/method mid-job.
9. City A missing June 2 and B missing June 3 retain independent counts; common-date statistics exclude both dates for that metric. Same grid for two cities is disclosed. Old v1 golden outputs and cached-job interpretation remain unchanged.

Validation performed for this documentation: primary-source review and offline arithmetic/calendar spot checks. No application implementation, provider availability proof, scientific accuracy validation, tests/build, services or dependency changes claimed. Provider availability and lead's shared-contract/resource choices remain integration gates.

## Implemented pure v2 boundary — September 13, 2026

The delegated implementation is now `packages/contracts/src/climate-comparison.ts` and `packages/comparison/src/climate.ts` with focused tests in `climate.test.ts`. The earlier proposal above remains preserved as research; this section states the narrower delivered pure-library behavior. API, worker orchestration, CSV, source access, UI and deployment belong to the lead and are not established by these tests. Existing v1 schemas/exports/aggregation are unchanged.

Exports: `ClimateQuerySchema`, `ClimatePlanDataSchema`, `ClimateResultSchema`, `ClimateSummarySchema`, `ClimateDaySchema` and matching schema-derived types; pure functions `createClimatePlan(query)`, `aggregateClimate(plan, [{chunkId,data}])`, `summarizeClimateDays(hours,timezone,startDate,endDate)`, plus canonical `ClimatePlanSchema` and `ClimateError`. Imports currently use disjoint source files; package index exports remain lead-owned.

- Period is 1–366 inclusive local dates, 2–5 distinct locations with immutable IANA timezone strings. Climatology mode is separately labeled, accepts 2–5 full common calendar years and pools underlying days; it is not a climatological normal. All local dates are examined at planning; skipped dates fail explicitly. Windows preserve the first and final resolved UTC instants. Runtime timezone data resolves intermediate dates; its version is not persisted, so migration across tzdata versions needs a separate reproducibility review.
- UTC source chunks are nonoverlapping, at most 31 dates / 744 rows, bounded to 305 chunks total. The envelope includes each city's final closing interval endpoint. A local selection requiring UTC data before 1940 rejects. Planning has no clock/provider calls: **the API/worker must validate `plan.fetchEndDate` against archive availability, including the padded closing date.** Canonical plan checking rejects modified windows/chunks/timezones; source schema rejects incorrect fixed provider URLs, units, grids, methods and missingness. Every planned chunk is mandatory exactly once. Null source measurements are valid partial data; missing delivery is an error.
- Daily instant slots are `ceil(start/hour)` through `<end`, preserving 23/24/25-hour days and fractional offsets. Daily precipitation/sunshine use fully contained preceding-hour intervals ending `start+1h` through `end` when aligned. Contrary to the initial proposed whole-selection rejection, fractional civil boundaries disable **only** complete interval totals: available sums include fully contained hours, `intervalAligned:false` and `unsupportedDays` expose unsupported boundary slivers. Instantaneous temperatures remain eligible. Expected interval slots count contained whole intervals only; slivers are never prorated or mislabeled as absent source records.
- Eight numeric metrics retain separate valid/expected/absent/null counts. `mean`, `avgDailyHigh/Low`, `min/max` and `total` period headlines require every selected day to be complete for that metric. `availableCompleteDays` averages only complete days; `availableMin/Max` use available hourly samples even on incomplete days. `sumAvailable` is the unscaled available interval total, nullable when no valid intervals exist. Zero remains zero. `validDays` is the complete-day denominator. `validYears` counts complete selected year groups (year-month groups inside monthly buckets), against `summary.years`; partially selected years are never labeled complete calendar years.
- For temperature, dew point, ordinary wet bulb, humidity, wind and cloud, mean means equal-day average of daily hourly means. For precipitation/sunshine, mean is average **daily amount/duration** (mm/seconds). Average daily high/low are populated only for the three temperature fields. Extremes are hourly-sample values, with earliest UTC timestamp, represented local date and exact unrounded tie count; render the UTC instant in the location timezone for local clock/offset. An interval extreme's localDate denotes its represented day, so its closing-midnight timestamp can fall on the next civil date. These are never between-hour or all-time records.
- Overview weights every underlying complete local date equally; months are not equally weighted. Period monthly keys are `YYYY-MM`, chronological, at most 13. Multiyear monthly keys are `01`…`12`, pooling same-calendar-month dates across years, with the actual contributing year list and complete-year-group coverage. Available wet-bulb hourly samples yield exact nearest-rank p50/p90/p95 for up to five years; no averaging monthly percentiles, approximation or WBGT substitution.
- Precipitation-day ≥1mm and six cloud bins retain the primary-source definitions above. Wet/below-threshold/unknown and six cloud counts/unknown independently partition dates. Sunshine is numeric duration, not an invented sunny-day category. No weather-code inference or thunder-day claim is added. Provider ordinary wet bulb is retained without local fallback, pressure correction or scientific domain-validation claim.
- Saved output has only city overview/monthly summaries and source evidence, no raw hours or daily arrays. Fixed per-city provenance is stored once as `location.source`; `location.sources` retains `{chunkId,retrievedAt,requestUrl}` for every chunk. Exact queries are in `result.plan.chunks` keyed by chunkId. Fixed provenance must match across chunks, so compaction cannot conceal changes. A 5-city × 5-year fixture occupies 607,557 bytes / 27,086 JSON nodes; a 1,827-day stress case with maximum-length multibyte IDs/names and full-precision numeric fields occupies 878,962 bytes. Runtime rejects output beyond the existing 1,000,000-byte / 100,000-node bound; no storage limits were raised.

Validation uses deterministic synthetic fixtures, never labeled live: DST spring/fall; closing-midnight assignment; fractional offsets; skipped dates and source-start guard; null versus absent versus zero; daily means versus average daily highs versus sampled extremes; earliest/tied extrema; leap-February/day weighting; exact precipitation/cloud boundaries; nearest-rank distributions and no-data; query/chunk/source/grid corruption; reversed chunk delivery; full five-year pooled month support and JSON bounds. Focused climate, existing v1 comparison and local-calendar tests are run with `npx tsx --test packages/comparison/src/climate.test.ts packages/comparison/src/index.test.ts packages/comparison/src/local-calendar.test.ts`; root `npm run typecheck` also passes at the delegated checkpoint. No live calls, new dependency, service, schema migration, index/root export or API/web modification is part of this handoff.

Not implemented in this bounded library: common-complete-local-date support across cities, saved timezone-database version/all daily boundaries, multidecade normals, station/model blending, inferred wet bulb, histogram, or climate ranking. Individual complete-day counts remain explicit; UI must not infer comparable support or rank cities merely because available means exist. Final build, API availability/budgets/cancellation, CSV and browser acceptance remain integration responsibilities.
