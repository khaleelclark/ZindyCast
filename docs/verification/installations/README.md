# Installation credentials and job ownership foundation

Verified September 11, 2026, using installed Node 22.22.1 and existing dependencies. Owned implementation: `packages/installations/src/index.ts` and `installations.test.ts`. No REST, browser storage, subscriptions, notification delivery, provider work, or services implemented here. N1 overall remains open.

## API and credential handling

`new InstallationRepository({path, clock?, busyTimeoutMs?, maxInstallations?, maxActiveJobs?, maxJobsPerInstallation?, maxJobMappings?, maxDiskBytes?})` opens a dedicated persistent SQLite DB. Use the same path and configuration for API/worker. Do not reuse the jobs/cache DB. Methods are synchronous; lock/capacity/configuration errors throw and must be caught at the boundary.

- `register(ttlMs): Registration` creates UUID ID plus independent 32 random bytes (256-bit secret), and returns `{id,bearer,createdAt,expiresAt}`. Explicit TTL from 1ms to 365 days. Bearer format is `id.base64urlSecret`. Only this method returns the secret. Server persists SHA-256 of the full bearer; the random secret is not a human password. IDs alone never authenticate.
- `parseBearerHeader(header): string|null` accepts a single `Authorization: Bearer <bearer>` header. `authenticate(bearer): Installation|null` returns only public ID/times. Expiry is exclusive (`now >= expiresAt` denies). Validly shaped tokens use equal-length `timingSafeEqual` digest comparison, including missing IDs. This does not promise constant-time database lookup or endpoint behavior.
- `revoke(bearer): boolean` immediately invalidates the credential; `delete(bearer): boolean` authenticates and removes the registration and mappings. Revoked/expired records can no longer authenticate for deletion and are removed by trusted cleanup.
- `reserveJob(bearer,jobId,expiresAt): boolean` authenticates inside `BEGIN IMMEDIATE`, reserves active capacity, and durably binds the globally unique ID to the installation. Expiry must be future, at most 30 days away, and within credential validity. False means invalid credentials, duplicate ID, or count limit. Invalid arguments and disk pressure throw. Every retained duplicate ID is denied, even for the same owner.
- `authorizeJob(bearer,jobId): JobOwnership|null` rechecks authentication and ownership and returns `{installationId,jobId,createdAt,expiresAt,active}`. Completed mappings remain readable until expiry. Unauthorized, missing and expired ownership all return null. Public installation IDs cannot be used in place of bearer credentials.
- `releaseJob(jobId): boolean` is TRUSTED SERVER/WORKER ONLY. Marks the reservation inactive without removing read ownership. Never expose this directly as a client operation. Only call after confirmed terminal job state or definite enqueue failure. Repeated release returns false.
- `usage()`, `diskUsage()`, `cleanup(batchSize=100)`, `close()` support bounded maintenance. Cleanup removes expired mappings and expired/revoked registrations, with cascading mapping deletion. Counts returned for `jobMappings` exclude cascades.

## Required integration order and crash handling

Authenticate every protected request using the bearer header, never an installation ID from a JSON body. Generate a new UUID job ID on the server; do not let clients claim arbitrary existing JobRepository IDs. Reserve ownership/admission **before** enqueueing that ID into JobRepository, using exactly the same expiry. If enqueue definitely failed, release the reservation; on an ambiguous failure retain it until reconciled. Do not enqueue if reservation was denied or threw. Never reuse an ID, even after mapping expiry/cleanup; JobRepository retention must not exceed ownership retention.

The worker should only run jobs having a valid server-owned mapping. Protect job detail, result, CSV, cancellation and any retry route with `authorizeJob` before accessing JobRepository. Recheck ownership immediately before a mutation where concurrent revocation matters; no cross-database atomic authorization guarantee is made. Do not send internal repository/lease details to the browser. Terminal release must follow JobRepository completion/failure/cancellation; cancellation must fence/abort execution first. Never release merely because a worker lease expired: recovered running work still consumes capacity.

There is no transaction across the installation and job databases. Crash before enqueue leaves a charged orphan; crash after a terminal write leaves a charged terminal job. Conservative default: keep the reservation until its original job expiry. A future trusted reconciler may release only after proving the job absent with no pending enqueue, or terminal with no pending retry. No automatic early orphan timeout is implemented. Stopped-producer reconciliation is an operational alternative. Retry of a released mapping is deliberately unsupported: create a new server-generated job ID and reserve it anew, or implement a coordinated fenced readmission protocol before enabling same-ID retries. Do not call JobRepository.retry on an inactive reservation.

Before registration deletion/revocation, integration must arrange cancellation of owned jobs (and later deletion of subscriptions). The repository only invalidates access/removes mappings; it cannot stop workers. Cleanup/deletion can therefore leave unowned jobs, which workers/reconciliation must cancel or skip. Global JobRepository capacity/quota limits remain essential. Unauthenticated registration must also receive API rate limits/global admission; per-installation limits alone do not prevent repeated-registration abuse. Do not advertise this module as complete endpoint security.

## Bounds and persistence

Defaults: 100 installations, 3 active unexpired jobs per installation, 100 retained mappings per installation, 1000 mappings globally, 32MiB disk admission budget. Count limits include retained expired/revoked rows until cleanup; terminal release does not bypass retention caps. Active capacity excludes exactly expired jobs. Options are validated and persisted; incompatible connections fail closed. A persisted mutation clock rejects backwards clock movement. Read-only calls do not advance its high-water mark.

WAL/FULL, foreign keys, 1s busy timeout (configurable 0–5s), 256-page autocheckpoint, 1MiB journal-size target, SQLite page cap, pre-insert combined database/WAL/SHM admission. These are not a hard filesystem quota: transaction/WAL overshoot and long-lived readers can exceed admission targets; database high-water pages remain allocated. Cleanup attempts a truncating checkpoint and reports `checkpointBusy`. Cleanup handles at most the requested number of explicit mapping/installation rows, but installation cascades may delete up to the bounded global mapping count. Schedule maintenance and monitor actual files; backup/restore, abrupt-crash, disk-full, and compaction procedures remain unverified. Revocation/deletion is logical removal, not guaranteed erasure from old database pages/backups.

The API should return registration once with `Cache-Control: no-store`, redact Authorization/registration bodies from logs, use private HTTPS and same-origin restrictions, and exclude protected resources from service-worker caches. Those controls are integration work. A localStorage/IndexedDB bearer is accessible to same-origin JavaScript and can be stolen by XSS; there is no hardware binding. Clearing browser storage loses access, without account recovery or cross-device sync. Tokens are returned in memory during registration and must never be logged. OS permissions and backup confidentiality are deployment requirements; this module does not configure filesystem ownership.
